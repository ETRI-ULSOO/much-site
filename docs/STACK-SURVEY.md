## 1. 요구 조건

[[SITE-ANALYSIS]]가 밝힌 현행 사이트의 문제와 사용자 결정에서 나온 조건이다.

| 번호 | 조건 | 나온 곳 |
|---|---|---|
| R1 | 한국어와 영어가 한 원천에서 갈라져 나와야 한다 | 현행 사이트가 영문판을 따로 복제해 이미 내용이 어긋났다 |
| R2 | 페이지마다 설명 태그와 대체 텍스트를 넣을 수 있어야 한다 | 현행 사이트는 넣을 수단 자체가 없다 |
| R3 | 3차원 뷰어와 지식그래프 탐색기를 나중에 심을 수 있어야 한다 | Google Sites는 자바스크립트를 넣지 못한다 |
| R4 | 서버 없이 GitHub Pages로 배포할 수 있어야 한다 | [[DECISIONS#P0-2. 호스팅 — 정적 사이트 + GitHub Pages\|P0-2]] |
| R5 | 두 대의 컴퓨터에서 같은 결과가 나와야 한다 | 맥북과 연구소 PC를 함께 쓴다 |
| R6 | 논문·특허·수상 같은 표 데이터를 다루기 편해야 한다 | 성과 아카이브가 사이트의 중심이다 |

## 2. 후보 비교 (2026-09-10 조사)

실행 가능성 열은 **이 환경에서 실제로 돌릴 수 있는가**를 뜻한다. 돌릴 수 없는 후보의
장점은 판단 재료가 되지 못한다.

| 후보 | 이중언어(R1) | 데모 삽입(R3) | 표 데이터(R6) | 의존성 | 실행 가능성 | 판정 |
|---|---|---|---|---|---|---|
| **Astro** | 공식 i18n 라우팅, 콘텐츠 컬렉션 내장 | 가장 강함. 필요한 부분만 자바스크립트를 붙이는 방식 | 콘텐츠 컬렉션이 YAML을 스키마로 검사한다 | Node와 npm | **실증됨** — 자매 과제가 이미 운영 중 | **채택** |
| Hugo | 내장 `languages`, hreflang 자동 | 순수 HTML이라 자유롭게 넣을 수 있다 | `data/*.yaml` | 실행 파일 하나 | 설치만 하면 됨 (2026-09-11 맥북에 0.166.0 설치함) | 기각 |
| Python + Jinja2 | 직접 구현해야 함 | 자유 | 직접 구현 | 파이썬만 | 가능 | 기각 — 언어 전환·사이트맵·이미지 처리를 전부 손수 만들어야 한다 |
| Eleventy | 공식 기능 없음 | 자유 | 가능 | Node | 가능 | 기각 — Hugo 대비 이점이 없다 |
| MkDocs Material | 플러그인 | 약함 | 약함 | 파이썬 | 가능 | 기각 — 문서 사이트 외형이 고정되어 시각 정체성 목표와 충돌한다 |

## 3. 2026-09-10 판정: Hugo (뒤집힘)

당시 근거는 세 가지였다. ① 실행 파일 하나면 두 컴퓨터를 맞출 수 있다. ② 이중언어
기능이 가장 성숙하다. ③ 이미지 처리가 내장이라 발표자료에서 뽑은 그림을 바로 웹용으로
만들 수 있다.

**이 판정은 "작업 폴더가 비어 있고 선례가 없다"를 전제로 삼았다.** 그리고 그 전제가 틀렸다.

## 4. 2026-09-11 재조사: 전제가 틀렸다

0단계 착수 중 같은 컴퓨터의 다른 폴더에서 자매 과제 CHIC의 홈페이지를 발견했다
(2026-09-11 실측).

| 항목 | 실측값 |
|---|---|
| 저장소 | `ETRI-ULSOO/CHIC-Homepage` (MUCH와 같은 조직) |
| 스택 | Astro 7.1.6, Node 22를 `.nvmrc`로 고정 |
| 배포 | `https://etri-ulsoo.github.io/CHIC-Homepage/`, GitHub Actions 워크플로 방식 |
| 이중언어 | `/ko/`·`/en/` 완전 대칭. 페이지 파일을 복제하지 않고 `[locale]` 라우팅 한 벌로 처리 |
| 운영 | 같은 사용자가 맥북과 연구소 PC 두 대로 운영 중 |

세 근거가 차례로 무너졌다.

1. **두 컴퓨터 맞추기**: 이미 Node 22로 맞춰 운영하고 있으므로 새로 지는 부담이 아니다.
   오히려 Hugo를 고르면 **두 가지 도구를 동시에 관리**하게 된다.
2. **이중언어 성숙도**: 작동하는 구현이 성숙도 비교를 대체한다. CHIC이 R1을 이미 풀었다.
3. **이미지 처리**: Astro에도 이미지 최적화가 내장되어 있어 차이가 결정적이지 않다.

여기에 더해 결정적인 근거가 하나 있다. [[DECISIONS#P0-1. 사이트 정체성 — 과제 시리즈 허브 + MUCH 성과 아카이브|P0-1]]에서
고른 **시리즈 허브 구조는 두 사이트가 같은 구조를 공유할 때에만 성립한다.** 생성기가
다르면 한쪽을 고칠 때마다 같은 수정을 두 벌로 해야 하고, 시간이 지날수록 두 사이트는 갈라진다.

## 5. 남길 교훈

**조사 범위를 작업 폴더 안으로 한정한 것이 원인이다.** 계획서를 쓸 때 "이 폴더가 비어
있다"를 "선례가 없다"로 읽었고, 같은 조직·같은 사용자의 자매 과제 저장소를 찾아보지 않았다.
후보군의 폭을 증명하지 않은 채 결론을 낸 셈이며, 이는 `~/.claude/rules/protocol.md`
G4.2가 경고하는 안티패턴에 해당한다.

일반화하면 이렇다. **기술을 고르기 전에 "같은 조직이 이미 비슷한 것을 만든 적이 있는가"를
먼저 묻는다.** 외부 선행 조사보다 이쪽이 먼저이고, 값이 훨씬 싸며, 발견되면 결론을 지배한다.
확인 수단은 세 가지다. ① 같은 계정의 저장소 목록 확인, ② 작업 폴더의 형제 폴더 확인,
③ 사용자에게 직접 묻기.

Hugo 0.166.0은 2026-09-11 맥북에 설치되어 있으나 이 프로젝트에서는 쓰지 않는다.
